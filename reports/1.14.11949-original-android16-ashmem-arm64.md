# Oxide 1.14.11949 — Android 16 ARM64 original game on Redroid with ashmem

Data: 14/10/2026 UTC. All execution hosted in GitHub Actions Linux ARM64.
No physical phone; four signed APK splits remained unchanged.

## 1. Android 16 host compatibility correction

Previous tests on native Azure ARM64 Linux kernel 6.17.0-1022-azure
showed no /dev/ashmem, no ashmem_linux module in distribution packages,
and SurfaceFlinger/zygote restart loops on Android 16:
- [Initial failed boot](https://github.com/48348484488/oxide/actions/runs/38611754822).
- [Host module inventory](https://github.com/48348484488/oxide/actions/runs/38613133772).

The pinned, unmerged upstream [redroid-modules PR #23](https://github.com/remote-android/redroid-modules/pull/23)
source commit f55e1e7515a6dd5f8e0f9569ea79148c08f60816 was first
[compiled only](https://github.com/48348484488/oxide/actions/runs/38613318778).
The disposable Linux ARM64 runner then loaded its ashmem_linux.ko using
the exact running kernel headers and exposed /dev/ashmem (misc device
major/minor 10:263) to the stock Redroid Android 16 container.

[Independent real boot #38613931053](https://github.com/48348484488/oxide/actions/runs/38613931053):
- sys.boot_completed = 1;
- ro.build.version.release = 16;
- ro.product.cpu.abilist = arm64-v8a;
- init.svc.zygote = running;
- init.svc.surfaceflinger = running;
- ActivityManager responded;
- Docker container running and not OOM-killed.

This confirms a real boot with ashmem on this disposable runner.
The kernel-module PR remains unmerged; it is not a production dependency
recommendation. No Android framework code, SurfaceFlinger or protection
logic was patched.

## 2. Unmodified original Oxide installed and executed

[Real original game test #38614441183](https://github.com/48348484488/oxide/actions/runs/38614441183):
All four original signed APK splits were SHA-256 checked, installed
using adb install-multiple, then the game's own launcher Activity was
started on the native ARM64 Android 16 virtual guest.

Forensic original process timeline:

| Android 16 original event | UTC |
|---|---|
| Activity PID 2099 launched | 18:23:22.669 |
| Activity completed/finished | 18:23:27.222 |
| Game PID 2099 sent SIGKILL 9 to itself | 18:23:27.225 |
| Android recorded death of PID 2099 | 18:23:27.274 |

The original self-signal occurred +4556 ms after Activity start and
three milliseconds after its finish. The initial Activity and process
were not alive/resumed at the 10s or 35s checkpoints.

The actual screenshot at +2s shows the original loading artwork,
a system 'Viewing full screen' guidance dialog and an Oxide-affiliated
Toast reading 'Security Threat Detected by App' with a per-run reference.
This warning is observed visually but the exact rule responsible was
not measured and its reference value does not establish a root cause.

Classification: ORIGINAL_ACTIVITY_SELF_SIGKILL.

## 3. Comparison and boundaries

In the previously tested Android 15 native ARM64 guest, original
Activity PID 1983 emitted self-SIGKILL after +4619 ms
([original run #38610951671](https://github.com/48348484488/oxide/actions/runs/38610951671)).
In Android 16 it happened after +4556 ms, about 63 ms earlier,
which is normal run-to-run timing variation and does not identify
the rejection mechanism.

Fixing Android 16's host shared-memory prerequisite **solved Android
boot**, not the application's own early termination. There is no
proof of Play Integrity verdict, a specific security cause, playable
multiplayer, live remote player coordinates or ESP inside the real game.

Next: maintain a strict distinction between verified native Android
runtime compatibility and the original application's own decision
to exit. Continue isolated, non-invasive diagnostics without assuming
which security control triggers the warning.
