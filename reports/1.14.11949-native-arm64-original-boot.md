# Oxide 1.14.11949 — Android ARM64 nativo no GitHub

**Data:** 13 de outubro de 2026. **Escopo:** execução dos 4 APKs originais, intactos, em Android 13 (`redroid`) sobre hardware AArch64 de GitHub Actions.

## Ambiente estabelecido

1. O runner `ubuntu-24.04-arm` usa CPU AArch64 e kernel Azure `6.17.0-1022-azure`.
2. O kernel configurado com `CONFIG_ANDROID_BINDER_IPC=m` precisava do módulo `binder_linux`. Instalamos `linux-modules-extra-6.17.0-1022-azure`; `binderfs` montou corretamente. Evidência: https://github.com/48348484488/oxide/actions/runs/38467302424
3. Um Android 13 `redroid/redroid:13.0.0_64only-latest` iniciou em contêiner ARM64: `sys.boot_completed=1`, ABI `arm64-v8a`, ADB `127.0.0.1:5555`. Evidência: https://github.com/48348484488/oxide/actions/runs/38467545745

## Investigação atual

A workflow `.github/workflows/redroid-original-smoke.yml` foi aprimorada para coletar o PID a cada segundo, um screenshot no segundo 2, informações de memória, `dumpsys activity exit-info`, `logcat -b crash` e `logcat -b events`.

**Não existem dados de posição de outros jogadores, câmera ativa de partida nem ESP em funcionamento.** A biblioteca JNI/Canvas verificada anteriormente pertence a outro APK isolado.

**Próximo marco:** descobrir se o Oxide encerra por comando interno ou por condição externa do ambiente e conseguir mantê-lo aberto em modo legítimo, sem modificar nem contornar a proteção do jogo. Mesmo que o processo permaneça ativo, isso não prova que o menu multiplayer funciona.

## Third test: 1-second process sampling and on-screen security warning

Run: https://github.com/48348484488/oxide/actions/runs/38468783338  
Artifacts: https://github.com/48348484488/oxide/actions/runs/38468783338/artifacts/11851021272

This is **observed UI text**, not an interpretation of a stack trace. The screenshot is retained as `screen_2s.png` inside the Actions artifact.

- 21:13:30, PID 2096, RSS 696228 KB, 127 threads.

The independent Android `dumpsys activity exit-info` confirms:

This is consistent with the app displaying a security warning before terminating. **It does not identify the triggering condition**, establish which component sent SIGKILL, or imply that memory pressure, Google Play absence, emulator fingerprints, or ARM64 compatibility alone are responsible. Do not report any of those as proven root cause.

The trace shows the unmodified game's loading image, not a playable menu; no server connection, active gameplay camera, remote player coordinates or working ESP.

### Current engineering boundary

Further progress on an actual playable Oxide build requires an authorized environment where the game passes its built-in security checks without patching or disabling them. A new headless Linux/Android runner alone does not supply the needed player telemetry. The established independent C++/JNI/Canvas bridge remains test-only.


## Follow-up: direct SIGKILL emitter evidence from original artifact

The unmodified-app artifact of run [38468783338](https://github.com/48348484488/oxide/actions/runs/38468783338) was inspected directly (not only the Actions console). In `logcat.txt`:

```text
10-13 21:13:33.483  2096  2096 I Process : Sending signal. PID: 2096 SIG: 9
10-13 21:13:34.025   228  2041 I Process : Sending signal. PID: 2096 SIG: 9
```

Android `logcat -v threadtime` prefixes entries with **emitting PID** and TID. The first entry is emitted by the Oxide process **2096** and targets **2096**. This is **positive evidence that the app process itself invoked/logged a self-directed SIGKILL**, prior to the later system-process entry (PID 228). The earlier formulation that the signal sender was entirely unknown was overly cautious.

This observation does **not** isolate the internal component or exact condition which caused the app to request termination. Its proximity to the on-screen *Security Threat Detected by App* message strongly supports a connection, but without an app-authorized diagnostic channel the specific validation failure is still unproven. The resident-memory measurement near 973 MB is not independent proof of out-of-memory termination.

Non-invasive follow-up instrumentation now captures continuous `logcat -b all`, host-kernel OOM evidence, guest memory state, and a process-emitter-versus-target PID comparison. It does not modify game APKs or disable security protections.

- Instrumentation change: [603330b](https://github.com/48348484488/oxide/commit/603330b71b6b088f1d0d5c4fefb8d5eb97d38bea), run [38469770255](https://github.com/48348484488/oxide/actions/runs/38469770255)
- Correct self-signal classifier: [efbf359](https://github.com/48348484488/oxide/commit/efbf3594f1718f80951277112ea57c650fee76ad), run [38470052037](https://github.com/48348484488/oxide/actions/runs/38470052037)

No original-game multiplayer gameplay or real-player ESP data have been captured.


## Repetition and PID classification correction

Run [38469770255](https://github.com/48348484488/oxide/actions/runs/38469770255) reproduced the self-directed signal, with a *different* original Activity process PID:

```text
10-13 21:21:12.565  2105  2105 I Process : Sending signal. PID: 2105 SIG: 9
10-13 21:21:13.096   230  2055 I Process : Sending signal. PID: 2105 SIG: 9
```

The matching `exit_info.txt` records PID **2105** as `reason=2 (SIGNALED), status=9`. The new host-kernel OOM keyword extraction had **no matches in the collected tail**; this is additional negative evidence, not proof that OOM is impossible.

**Important test correction:** PID **2539** appeared at the 10-second sampling point, but `am_proc_start` identified it as a separate instance launched for `com.google.android.gms.measurement.AppMeasurementJobService`. It later ended via `EXIT_SELF`. The old checker incorrectly reported `EXITED_BETWEEN_10S_AND_35S` from the existence of any package PID. PID 2539 was not evidence that the `OxideActivity` was still running.

Workflow fix [7daa636](https://github.com/48348484488/oxide/commit/7daa636e4784fd9f5e0cd73977396491585f0de3) now classifies the **initial Activity process** separately from any subsequent analytics process, and checks the top resumed Activity at 10 and 35 seconds. An intentional CI failure here means the game's startup criterion was not met; it does not mean that APK installation or the diagnostic harness failed.
