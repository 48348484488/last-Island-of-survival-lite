### What actually works now

- A single Android WindowManager.TYPE_APPLICATION_OVERLAY Service is
  started **once**; Java receives a controlled input sequence from
  privileged Android shell broadcasts using a separate BroadcastReceiver.
- Broadcast sender permission in AndroidManifest is
  `android.permission.DUMP`; ordinary third-party senders without that
  permission cannot use this diagnostic receiver.
- The receiver accepts a strictly increasing sequence number, finite,
  bounded x-position and nonnegative bounded age. Inputs are handed
  to JNI C++ nativeProjectSnapshot and visualized by invalidating the
  SAME Android View, without recreating the overlay window.
- A stale synthetic sample older than max_age_ms=250 returns no
  rectangles and clears the existing marker.
- A replay with the old sequence number 2 is explicitly rejected; the
  previously cleared screen remains empty.
- A later valid sequence 3 restores the marker at a new position.
- The explicit sequence 4 stop removes the Android window.

## Important distinction

This **proves the diagnostic overlay's input → JNI projection → Android
WindowManager → screenshot pipeline** can respond to independently
delivered synthetic position samples in a real virtual ARM64 Android
session. It is **not** evidence of a live Oxide multiplayer match,
actual enemy coordinates, real-player ESP, a working APK-modification
strategy, or ability to pass the original game's security checks.

The original unmodified Oxide APK still displays a security warning
and self-kills on native virtual Android 12/13/14 under the conditions
tested. No bypass, spoofed identity, altered game bytes or physical
Android device was used.

## Source and reproducibility

- `esp_core/android_probe/src/com/oxide/bridgeprobe/OverlayProbeService.java`
  implements the single running overlay, freshness cutoff, sequence guard
  and JNI frame projection.
- `esp_core/android_probe/src/com/oxide/bridgeprobe/SyntheticFeedReceiver.java`
  handles privileged-shell-only test broadcasts.
- `esp_core/android_probe/virtual_overlay_feed.sh` sends controlled
  snapshots and captures each real screenshot.
- `esp_core/android_probe/check_virtual_feed_control.py` asserts
  actual phase logs, replay rejection, screenshot geometry, process
  stability and original game's absence.
- `esp_core/android_probe/tests/test_virtual_feed_control.py`
  regression-tests fail-closed cases.

## Later verified: autonomous stale overlay expiry when feed disconnects

[Real virtual ARM64 Android13 run #38549706831](https://github.com/48348484488/oxide/actions/runs/38549706831)
completed **SUCCESS** (both native APK build and Android runtime).
[Updated true screenshots and verdict artifact](https://github.com/48348484488/oxide/actions/runs/38549706831/artifacts/11885992963).

The diagnostic Service now schedules a 4-second main-thread idle
watchdog while an external ADB shell feed is active. Each validated
strictly newer sample re-arms this watchdog. If the producer silently
stops, WITHOUT sending a synthetic stale sample, the Service
automatically clears all projected marker coordinates and redraws the
same view. The original Service remains alive and retains the SAME
Android process PID; the idle handler is removed on Service destruction.

The real virtual Android execution repeated initial → moved →
explicitly stale → duplicate rejected → restored, THEN deliberately
stopped sending frames. The test captured an additional SILENT
screenshot and verified:

- exactly one `RESULT=PASS FEED_IDLE_TIMEOUT RECT_COUNT=0` log;
- **0 projected green pixels** in the SILENT screenshot;
- identical original diagnostic service PID before and after timeout;
- original ADB replay/monotonic checks still passed;
- later explicit stop also removed the overlay;
- no original game APK installed or executed.

The native runtime test suite passed 7+6+7=20 regressions. The build
suite additionally exercised five original screen composition tests,
all with a separately compiled and signed JNI ARM64 APK.

This closes a real display-safety hole: a producer crash or data-stream
disconnect no longer leaves an old synthetic projected marker visible
indefinitely. The four-second limit is a diagnostic configuration and
not a claim of network player-update latency or real-game integration.

**Still NOT demonstrated:** original Oxide multiplayer compatibility,
authorized real-game player positions, in-game ESP functionality,
or bypassing the original game's protection. This enhancement was
tested exclusively against an independent lab APK on virtual ARM64
Android 13.
