The scanner interprets UnityFS's big-endian blocks and directory
metadata and uses bounded LZ4 raw-block decompression for UnityFS LZ4 and
LZ4HC data. Streamed blocks are scanned with overlap between blocks,

explicitly counted and cannot be misreported as scanned.

### Format-8 Unity 6000 metadata size anomaly

The first run [#38539324246](https://github.com/48348484488/oxide/actions/runs/38539324246)
decoded **276/277 bundles**, scanning **1,437,446,393** bytes.
The remaining original Unity 6000 format-8 monoscripts bundle in
split_UnityDataAssetPack.apk declared a bundle length of **109,143**
bytes, but the true signed APK ZIP entry length is **109,127** bytes:
a **16-byte declared-length surplus**.

The final reader accepts this precise 16-byte discrepancy only for
format-7-or-newer UnityFS with blocks-directory metadata stored at
the **front**, and then validates that the entire declared compressed
index and *all indexed compressed data blocks* fit inside the **actual**
physical ZIP entry length, not the inflated Unity header size.
End-of-file metadata and other mismatches still fail closed.
Synthetic negative tests verify that a 17-byte mismatch or tail-metadata
truncation remains rejected. This correction allowed the final
all-277-bundle scan without changing any original bytes.

## Interpretation and limits

The full raw UTF-8 / UTF-16LE / UTF-16BE literal searches found no exact
warning text in any outer ZIP member, nor in the concatenated
decompressed *data blocks* of the 277 UnityFS bundles.

This is **not** proof that the security message cannot be encoded
inside a serialized Unity object, generated by native or managed
code, encrypted separately, assembled at runtime, or sent by a
remote service. Raw decoded data block scanning is not the same as
semantic decoding of every serialized Unity object or examining
arbitrary nested formats. The failure to match does not identify
which security component drew the Toast nor why it rejected the
virtual environment.

The original unmodified game still displayed its security notice on
Android 12/13/14 native ARM64 virtual Redroid and terminated its
own process; the block-level audit did not run or alter the game.

No security mechanism was bypassed or modified, no Android
identity/integrity claim was forged, and no player coordinates,
multiplayer gameplay, or actual in-game ESP has been validated.

## Practical development direction

The resource format uncertainty is now materially reduced; the remaining
obstacle to an original-game multiplayer/ESP validation is runtime security
rejection rather than inability to enumerate/scan the UnityFS assets.
Maintain these *separate* workstreams: (a) original game Android
compatibility and exact reproducible startup/exit evidence, respecting
protections; and (b) standalone overlay projection, graphics correctness,
and synthetic inputs in native virtual Android.
