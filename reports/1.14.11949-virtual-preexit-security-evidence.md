The native libc warning is:

    The property "ro.build.fingerprint" has a value with length 113 that is too large for __system_property_get()/__system_property_read(); use __system_property_read_callback() instead.

It occurred twice per original game process, starting ~449 ms after
PID 2197's Activity launch and ~435 ms after PID 2578's.
It suggests at least one native caller uses an Android property API
unsuitable for that long value, but **does not establish** whether
that caller is the shield, the game, another bundled SDK, or a crash trigger.

First Play Store warnings were ~184/186 ms after Activity start;
Unity logs and multiple graphics/sensor events occurred later, followed
by the original process self-directed SIGKILL about five seconds after
launch. Ordering and repetition cannot establish causation.

The exact game security rejection cause is NOT IDENTIFIED.

## External source on the wording — NOT vendor proof

Appdome's own published mobile-testing documentation uses the exact
user-facing warning wording "Security Threat Detected by App" as an
example of a protected application blocking testing, and explains that
emulators/debuggable/test automation can be rejected by protected apps.
Appdome's vendor-sanctioned Build2Test is a separate developer-controlled
configuration for approved testing of Apps protected by Appdome.

Sources:
- https://www.appdome.com/dev-sec-blog/ai-driven-scams-and-fraud/
- https://www.appdome.com/how-to/devsecops-automation-mobile-cicd/testing-secure-mobile-apps/appsec-release-orchestration-testing-protected-mobile-apps-test-appdome-secured-android-apps-by-using-saucelabs/

Crucial qualification: **this does not establish that Oxide uses Appdome**.
The verified original APK scan specifically searched for branding literals
"appdome", "oneshield", and "fusion set" in 1,454 ZIP members across
base.apk, split_config.arm64_v8a.apk, split_config.xxhdpi.apk.
No explicit branding indicators were found. The ~867 MB Unity asset
split was not part of the narrow branding test; string packing or custom
SDK integration also cannot be excluded. The protected game's vendor
and the specific detector are still **UNCONFIRMED**.

## Why current native virtual gameplay is not confirmed

- ARM64 Redroid Android 12, 13 and 14: original game loading UI and
  security toast appeared; original Activity self-SIGKILL verified.
  Android 12 exact Activity PID 1829 was cross-verified via ActivityRecord,
  31 samples, exit-info status 9 and game-PID logcat.
- Official x86_64 Google Play emulators Android 14–16: a DIFFERENT
  issue, where the Berberis ARM64 translator explicitly rejected an
  original loader MRS instruction, reproducing SIGILL independently.
- Google packages, Android permissions, graphics warnings and sensors
  are NOT enough to identify or fix the original app's security decision.
- No original game protection was disabled, patched, hooked or spoofed.
  No verified multiplayer session or actual player coordinate feed has
  been obtained. The previous loading screen diagnostic marker was synthetic.

## Practical next legitimate direction: virtual-only

Continue read-only native Android compatibility analysis and standalone
ESP overlay testability on ARM64 without pretending that a secure,
unchanged application is automatically expected to run in every emulator.
If the game's copyright/security owner has an authorized emulator-testing
build or testing policy, use that through the owner's supported channel;
never assume a production APK has such permission.

This project should not require a physical phone or a paid physical-device
lab. The old physical-ADB integration is not a dependency of current work.
