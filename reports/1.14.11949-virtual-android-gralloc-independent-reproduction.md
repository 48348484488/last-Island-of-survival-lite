# Oxide 1.14.11949 — Redroid independent graphic-buffer format verification

Date: 2026-10-14 UTC. **100% virtual**, no physical Android devices.

## Real original game observation

The authentic, unchanged Oxide 1.14.11949 game executed in Redroid
Android 13 native ARM64 and repeatedly logged:

    GraphicBufferAllocator: Failed to allocate (4 x 4) layerCount 1 format 43 usage b00: 3
    GraphicBufferAllocator: Failed to allocate (4 x 4) layerCount 1 format 56 usage b00: 3

These errors came from the original game's process in the
[real two-launch experiment #38478578089](https://github.com/48348484488/oxide/actions/runs/38478578089)
and persisted before and after all four tested normal Android
runtime permissions were granted.

Android publicly documents AHardwareBuffer format 43 as the 10-bit RGBA
1010102 format, and format 56 as R8 (single-channel 8-bit).
Reference: https://developer.android.com/ndk/reference/group/a-hardware-buffer

## Separate real Android graphics allocation reproduction

[Original-independent Android 13 CI run #38490256931](https://github.com/48348484488/oxide/actions/runs/38490256931)
completed successfully. The test was a newly created, independently
signed standalone Java app, PID **1631**, using Android's public
HardwareBuffer.isSupported/create APIs.

The original Oxide **was NOT downloaded, installed or executed**.
The same ARM64 Redroid Android 13 graphics mode was tested.
Six diagnostic classifier unit tests passed on both the x86 build runner
and the ARM64 experiment runner.

Actual test dimensions: width=4, height=4, layerCount=1.

| Android hardware-buffer format | Usage | isSupported | create |
|---|---|---|---|
| RGBA1010102 (43) | 0xb00 | false | FAIL (IllegalArgumentException) |
| R8 (56) | 0xb00 | false | FAIL (IllegalArgumentException) |
| RGBA8888 (1) | 0xb00 | true | PASS |
| RGBA8888 (1) | 0x300 | true | PASS |
| RGBA1010102 (43) | 0x300 | false | FAIL (IllegalArgumentException) |
| R8 (56) | 0x300 | false | FAIL (IllegalArgumentException) |

The test app's own PID also logged four GraphicBufferAllocator errors.
This is an **independent reproduction** of the Redroid
unsupported-buffer-format problem with the precise original
dimensions/formats/usage, plus two meaningful positive controls.

The format 1 positive controls show that Android's graphic-buffer
allocator is functional for at least standard RGBA8888; the problem
is NOT blanket inability to allocate ANY graphic buffer.
Changing the usage parameter from 0xb00 to 0x300 did not make
formats 43 or 56 supported in this environment.

## Interpretation limits

- This proves a **virtual Android graphics compatibility limitation**,
  not why the original game detects a security threat.
- Generic Android renderer fallback behavior may let the game progress
  despite format allocation failure. The real original did render its
  loading image, and its own security toast subsequently appeared.
- The actual original-game self-SIGKILL was confirmed independently in
  Redroid ARM64 Android 12, 13, 14; the particular security check that
  led to that self-termination remains UNKNOWN.
- This experiment did not bypass protections, modify native libraries,
  alter Android identity, access real game data, or validate any
  multiplayer player coordinates / ESP.
- A generic public Redroid issue also contains the same 4x4 format 43
  usage b00 allocation failure from a separate Flutter application:
  https://github.com/remote-android/redroid-doc/issues/400

## Follow-up REAL virtual Android 12 and 14 comparison

[Actual GitHub Actions #38490502668](https://github.com/48348484488/oxide/actions/runs/38490502668)
finished **SUCCESS** with two real native ARM64 Redroid jobs:
Android 12 and Android 14. The same independently signed Java APK
from the Android 13 probe was reused; no original Oxide game assets
were downloaded, installed or executed, and each runner passed
six graphics parser regressions.

Exactly identical dimensions (4 x 4 x 1), numeric hardware-buffer
formats and usage flags were requested on all three Android versions.

| Buffer format | Usage | Android 12 | Android 13 | Android 14 |
|---|---|---|---|---|
| RGBA1010102 (43) | 0xb00 | PASS | FAIL | FAIL |
| R8 (56) | 0xb00 | FAIL | FAIL | FAIL |
| RGBA8888 (1) | 0xb00 | PASS | PASS | PASS |
| RGBA1010102 (43) | 0x300 | PASS | FAIL | FAIL |
| R8 (56) | 0x300 | FAIL | FAIL | FAIL |
| RGBA8888 (1) | 0x300 | PASS | PASS | PASS |

**New finding:** the unsupported graphic-buffer set is
**not identical in every virtual Redroid version**.
Android 12 supports the native 10-bit format 43 used in the
original game's error logs on Android 13, whereas Android 13/14
reject it. Format 56 remains unsupported in all three tested
virtual environments, and standard RGBA8888 works in all three.

The ORIGINAL game nevertheless showed its security-warning
loading screen and self-terminated in Android 12, where the
independent probe demonstrates that format 43 works.
This is strong reason to treat the 10-bit allocator limitation
as a **separate graphics compatibility defect** rather than
assume it independently accounts for the game's security rejection.

It does **not** prove that the actual original Oxide can allocate
every 10-bit buffer on Android 12: this test used a different app
context. Nor does it establish what other emulator condition or
app-side check caused the security warning.

[Native Android12 and Android14 controlled CI](https://github.com/48348484488/oxide/actions/runs/38490502668) |
[Original Android13 separate app comparison](https://github.com/48348484488/oxide/actions/runs/38490256931).

The next technical milestone must distinguish the unresolved
security rejection (requires appropriate authorized app test context)
from the independently reproduced graphics-format limitations;
do not conflate these or claim live multiplayer/ESP success.
